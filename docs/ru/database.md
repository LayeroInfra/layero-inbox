# База данных и доступ

Четыре миграции в `db/migrations`, применяются по порядку
(`layero db sql <база> --file …`, это делает `scripts/setup.sh`).

| Файл | Что делает |
|---|---|
| `0001_schema.sql` | Таблицы, проверки членства, триггеры, RLS |
| `0002_forms.sql` | `api.site_form`, `api.submit_form`, `api.accept_invites`, свободные слоты |
| `0003_storage.sql` | Политики приватного бакета `screenshots` |
| `0004_notifications.sql` | Telegram: текст, фото, подключение одной кнопкой |

Перед миграциями должен быть включён вход: схема `auth` и функция `auth.uid()`
появляются после `layero data enable --auth`.

## Таблицы

| Таблица | Строка — это | Ключевые поля |
|---|---|---|
| `sites` | сайт клиента | `owner_id`, `site_key` (публичный ключ для виджета), `forms`, расписание `booking_*`, `timezone`, `telegram_chat_id` |
| `site_members` | пользователь из команды сайта | `role`: `owner` или `member`; владелец добавляется триггером |
| `invites` | приглашение по почте | `email`, `accepted_at` |
| `reports` | сообщение с сайта | `kind`: `problem`, `lead`, `booking`; `status`; `screenshot_path`; `notified_at` |

Проверка `check` на `reports` требует для каждого типа своё: у проблемы — текст,
у заявки — контакт и согласие, у записи — ещё и время.

## Роли и права

| Действие | Посетитель сайта (`anon`) | Команда сайта | Владелец сайта |
|---|---|---|---|
| Читать сайты и сообщения | — | свои сайты | свои сайты |
| Отправить форму | `api.submit_form` | `api.submit_form` | `api.submit_form` |
| Менять статус сообщения | — | да | да |
| Менять текст сообщения | — | — | — |
| Удалить сообщение | — | — | да |
| Настройки сайта, приглашения, Telegram | — | — | да |
| Смотреть снимки | только свой, 1 минуту — для Telegram | да | да |

Как это устроено:

- **Посетителю сайта таблицы закрыты целиком** — `revoke all … from anon`. Всё, что он
  может, — вызвать две функции.
- **Вставка в `reports` с клиента закрыта** даже для вошедших пользователей: только через
  `api.submit_form`.
- **Менять можно только статус**: `grant update (status)` — права на уровне
  колонки. Попытка поменять `message` получает `403`, а не молчаливый ноль строк.
- **Проверки членства — функции SECURITY DEFINER** (`inbox_private.is_member`,
  `is_owner`). Иначе политика `sites` спрашивает `site_members`, а политика
  `site_members` — `sites`, и Postgres уходит в бесконечную рекурсию.
- **`site_members` пишет только база** — триггер при создании сайта и
  `api.accept_invites`. Вступить в чужой сайт вставкой строки нельзя.

## Функции SECURITY DEFINER: на что смотреть

Такая функция выполняется с правами владельца схемы и обходит RLS. Поэтому в
каждой:

1. `set search_path = public` — чтобы нельзя было подсунуть свою таблицу с тем
   же именем.
2. Все входные данные обрезаются и проверяются (`left(btrim(...))`, `check`).
3. Права проверяются явно: `inbox_private.is_owner(site_id)`, `auth.uid()`.
4. `#variable_conflict use_column` — аргументы называются как колонки
   (это контракт API), и без директивы `site_key = site_key` всегда истинно.

## Снимки в приватном бакете

Бакет `screenshots` — приватный, до 5 МБ, только JPEG и PNG. Путь файла —
`<site_id>/<report_id>.jpg`.

1. Виджет вызывает `api.submit_form(…, has_screenshot := true)` и получает
   `upload_path`.
2. Загружает файл по этому пути. Политика `screenshots_visitor_upload`
   пропускает только путь свежего (10 минут) сообщения, у которого файла ещё нет.
3. Подписывает ссылку на минуту — политика `screenshots_visitor_sign` — и
   передаёт её в `api.notify_screenshot`, чтобы Telegram скачал фото.
4. Команда сайта читает снимки через подписанные ссылки (`screenshots_member_read`),
   владелец может удалить (`screenshots_owner_delete`).

Первая папка пути — id сайта, её достаёт `inbox_private.screenshot_site`.

## Проверка прав

`scripts/check-access.sh` проверяет права через настоящий шлюз Data API:
`layero data probe` выполняет запрос от имени посетителя сайта или конкретного
пользователя, а запись откатывает.

```bash
LAYERO_ORG=my-team OWNER_EMAIL=me@mail.ru OTHER_EMAIL=stranger@mail.ru \
MEMBER_EMAIL=colleague@mail.ru ./scripts/check-access.sh
```

Нужны: владелец с сайтом и хотя бы одним сообщением, второй пользователь со
своим аккаунтом и, по желанию, пользователь из команды сайта, принявший приглашение.

```
Посетитель сайта (публичный ключ)
  ✓ не читает сообщения                         401
  ✓ не пишет в таблицу напрямую                 401
  ✓ не видит список сайтов                      401
Владелец сайта
  ✓ видит свой сайт                             200:1
  ✓ меняет статус                               200:1
  ✓ не меняет текст сообщения                   403
Пользователь из другой команды
  ✓ не видит чужой сайт                         200:0
  ✓ не видит чужое сообщение по id              200:0
  ✓ не меняет чужое сообщение                   200:0
  ✓ не удаляет чужой сайт                       200:0
  ✓ не добавляет себя в чужую команду           403
  ✓ не приглашает себя в чужую команду          403
  ✓ не создаёт сайт от имени владельца          403
  ✓ не видит снимки чужого сайта                200:0
Пользователь из команды сайта
  ✓ видит сайт                                  200:1
  ✓ меняет статус                               200:1
  ✓ не удаляет сообщение — только владелец      200:0
  ✓ не меняет настройки сайта                   200:0

Итог: 18 ✓, 0 ✗
```

`200:0` — запрос прошёл, но RLS отфильтровала все строки. Так Postgres
отвечает на «чужое»: строки для этого пользователя просто не существует.
